# プロジェクト仕様書 — 厚生部呼び出しシステム

最終更新日: 2026/04/07

---

## 1. 概要

### 1.1 目的

厚生部呼び出しシステムは、来場者または部員が傷病者対応を厚生部へ依頼し、厚生部側が対応状況を一覧で管理できる機能である。

現行システムでは、呼び出し作成時に最小項目だけを入力し、呼び出し後に本人が詳細情報を追記する。厚生部側は一覧画面から救護者設定と対応終了を行う。

### 1.2 実装方針

- フロントエンド: React Native (Expo)
- バックエンド: Supabase
- リアルタイム更新: `item2_calls` の Supabase Realtime 購読
- 通知: ERP 通知基盤 (`dispatch-notification` Edge Function)
- 実装ディレクトリ: `src/features/item2/`

### 1.3 現行スコープ

現行実装に含むもの:
- 呼び出し作成
- 呼び出し後の詳細入力
- 呼び出し履歴 / 対応一覧表示
- 救護者設定
- 対応終了
- 厚生部ロール向け通知

現行実装に含まないもの:
- チャット
- 既読 / 未読
- 画像送信
- 通話

## 2. 対象ユーザー

### 2.1 一般ユーザー

- 自分または他者の体調不良・怪我について厚生部を呼び出す
- 自分が作成した呼び出し履歴を確認する

### 2.2 厚生部ユーザー

- すべての呼び出しを対応一覧で確認する
- 救護者を設定する
- 呼び出しを対応終了に変更する

### 2.3 管理者

- 厚生部ユーザーと同等に対応一覧へアクセスできる

## 4. 機能要件

## 4.1 呼び出し作成

### 4.1.1 入力方式

- 一問一答形式ではなく、最初は最小入力で即送信できる
- テキスト入力項目は自由記述とする
- `場所` は必須入力
- `必要なもの` は任意入力とする

### 4.1.2 初回入力

1. `場所を入力してください`
   - 例: `11月ホール 2階 学友会連合会室前`
2. `必要なものを入力してください（任意）`
   - 例: `絆創膏、体温計`
   - 何も必要なければ `特になし`

### 4.1.3 作成時の保存内容

呼び出し作成時に以下を保存する。

- 呼び出し者ID
- 呼び出し者名
- 内部分類情報（画面には表示しない）
- 要約文 (`detail`: 初回は場所と必要なものの簡易要約)
- 場所
- 必要なもの (`assessment_answers.suppliesNeeded`, 任意)
- 詳細入力状態 (`detail_status = pending`)

### 4.1.4 詳細入力

- 呼び出し作成後、本人が詳細情報を入力する
- 詳細入力はモーダルで表示する
- 閉じる場合は入力内容を破棄する
- 厚生部側でも詳細情報を確認・編集できる
- 完了時に `detail_status = completed` に更新する
- 詳細入力で保存する主な項目:
  - `傷病者はあなた自身ですか？`（本人/他人）
  - `本人` の場合: `立てる/歩けるか`
  - `他人` の場合: `意識`、`呼吸`
  - `状態カテゴリ`
  - `状態カテゴリ` に応じた追加入力

### 4.1.5 詳細要約文の生成

`detail` には、入力内容から生成した要約文を保存する。

例:

```text
場所: 11月ホール 2階 学友会連合会室前
必要なもの: 絆創膏、体温計
傷病者: 本人ではない
意識: あり
呼吸: なし
状態: 体調不良
症状: 発熱、倦怠感
```

## 4.2 呼び出し一覧 / 履歴表示

### 4.2.1 一般ユーザーの履歴

- ログイン中ユーザーが作成した呼び出しのみ表示する
- タブ名は `履歴`
- `detail_status` が `pending` の呼び出しは一覧上で `詳細入力待ち` を表示する
- `detail_status` が `completed` の呼び出しは一覧上で `追加情報済み` を表示する
- 履歴カードから詳細を開き、内容を確認・編集できる

### 4.2.2 厚生部側の対応一覧

- すべての呼び出しを表示する
- 初期並び順は以下:
  - `未対応`
  - `対応中`
  - `対応終了`
- 同一ステータス内では `created_at` の降順

### 4.2.3 対応一覧の絞り込み

#### ステータス絞り込み

- `すべて`
- `未対応`
- `対応中`
- `対応終了`

### 4.2.4 一覧カード表示項目

- ステータスバッジ
- 要約文
- 場所
- 呼び出し者名
- 呼び出し者ロール
- 作成時刻
- 救護者名
- 詳細入力待ちバッジ（`detail_status = pending` の場合）

呼び出し者ロールは、`user_roles` と `roles` を参照して表示する。
ロールが存在しない場合は `なし` と表示する。

---

## 4.3 救護者設定

### 4.3.1 操作権限

- 厚生部ロールまたは管理者ロールを持つユーザーのみ実行可能

### 4.3.2 設定方法

- 一覧カードの `救護者設定` ボタンからモーダルを開く
- 複数人選択可能
- モーダルで `確定` を押した時点で保存する
- `戻る` を押した場合は保存しない

### 4.3.3 モーダル仕様

- モーダルタイトル: `救護者を選択`
- 候補ユーザー: `厚生部` および `管理者` ロールを持つユーザー
- ユーザー検索:
  - `名前で検索` 入力欄を持つ
  - 入力文字列に応じて候補を即時絞り込みする
  - 一致なしの場合は `該当する名前がありません。` を表示する

### 4.3.4 ステータス自動変更

救護者設定時のステータス遷移は以下とする。

- 現在 `未対応` かつ 救護者が1人以上設定された場合: `対応中` に変更
- 現在 `対応中` の場合: そのまま維持
- 現在 `対応終了` の場合: そのまま維持

### 4.3.5 監査ログ

救護者更新時は `item2_audit_logs` に `call_assignees_updated` を記録する。

---

## 4.4 対応終了

### 4.4.1 操作権限

- 厚生部ロールまたは管理者ロールを持つユーザーのみ実行可能

### 4.4.2 実行条件

- `対応終了` ボタンは、未終了の呼び出しに対して表示する

### 4.4.3 確認 UI

- `対応終了` 押下時は画面内モーダルを表示する
- 表示文言:
  - `確認`
  - `対応を終了しますか？`
- ボタン:
  - `いいえ`
  - `はい`

### 4.4.4 更新内容

- ステータスを `resolved` に更新
- `resolved_at` を現在時刻で保存
- `resolved_by` に実行者IDを保存

---

## 4.5 通知

### 4.5.1 呼び出し作成通知

呼び出し作成成功後、厚生部ロール所持者へ ERP 通知を送信する。

#### 宛先

- `厚生部` ロール所持者

#### 通知タイトル

- `厚生部呼び出し`

#### 通知本文

- `{呼び出し者名}さんから呼び出しが作成されました。場所: {場所}。必要なもの: {必要なもの}`
  - `必要なもの` が未入力の場合は `特になし` を使用する

#### metadata

- `type: item2_call_created`
- `call_id`
- `call_type`
- `status`
- `detail_status`
- `requester_name`
- `location_text`
- `supplies_needed`

### 4.5.2 通知失敗時の扱い

- 通知送信に失敗しても、呼び出し作成自体は成功扱いとする
- 失敗内容はクライアントコンソールに出力する

## 4.6 リアルタイム更新

### 4.6.1 対象

- `item2_calls`

### 4.6.2 用途

- 呼び出し一覧の自動更新
- 救護者設定後の一覧反映
- 対応終了後の一覧反映

## 6. データベース設計

## 6.1 使用テーブル

現行の `item2` で使用する主テーブル:
- `item2_calls`
- `item2_audit_logs`

補助参照テーブル:
- `user_profiles`
- `roles`
- `user_roles`

チャット関連テーブル:
- `item2_chat_rooms`
- `item2_chat_messages`
- `item2_chat_read_states`

上記チャット関連テーブルは `20260313_drop_item2_chat_tables.sql` で削除対象になっており、現行機能では使用しない。

### 6.2 item2_calls

| カラム名 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | uuid | Yes | 呼び出しID |
| requester_user_id | uuid | Yes | 呼び出し者ユーザーID |
| requester_name | text | Yes | 呼び出し者表示名 |
| requester_relation | text | No | `self` / `other` |
| call_type | text | Yes | `emergency` / `non_urgent` |
| purpose | text | No | 状態分類ラベル |
| detail | text | No | 要約文 |
| location_text | text | Yes | 場所 |
| detail_status | text | Yes | `pending` / `completed` |
| detail_completed_at | timestamptz | No | 詳細入力完了日時 |
| status | text | Yes | `unhandled` / `in_progress` / `resolved` |
| assigned_to | uuid[] | Yes | 救護者ユーザーID一覧 |
| assessment_answers | jsonb | No | 問診回答 JSON |
| resolved_at | timestamptz | No | 対応終了日時 |
| resolved_by | uuid | No | 対応終了実行者 |
| created_at | timestamptz | Yes | 作成日時 |
| updated_at | timestamptz | Yes | 更新日時 |

### 6.3 assessment_answers

`assessment_answers` には、フォームの回答一式を JSON で保存する。

主な格納例:
- `locationText`
- `suppliesNeeded`（任意）
- `summaryText`
- `requesterRelation`
- `consciousness`
- `breathing`
- `mobility`
- `conditionCategory`
- `symptoms`

### 6.4 item2_audit_logs

救護者更新時の監査ログを保存する。

主なカラム:
- `event_type`
- `call_id`
- `actor_id`
- `old_value`
- `new_value`
- `created_at`

## 10. 非機能要件

### 10.1 操作性

- モバイル端末で操作可能であること
- 選択肢は大きめのタップ領域を持つこと
- 入力フローは上から順に自然に進めること

### 10.2 保守性

- 問診の詳細回答は `assessment_answers` に JSON 保存し、将来の質問追加で DB 変更を最小限にする
- 一覧表示に必要な派生情報はクライアント側で整形してよい

### 10.3 障害許容

- 通知送信失敗で呼び出し作成を失敗させない
- 一部 migration 未反映環境でも最小限の呼び出し登録を継続できるようにする

### 10.4 Supabase 使用量目安

item2 単体で、11/1〜11/5 の5日間に連絡が 500 件来る場合の想定使用量は以下とする。

| 項目 | 想定使用量 | 補足 |
| --- | --- | --- |
| リアルタイムメッセージ(件) | 25,000件程度 | 呼び出し更新1件につき厚生部50名に配信される前提で、作成・詳細入力・更新を含む |
| エッジ関数(件) | 1,000件程度 | 呼び出し作成通知を厚生部50名へ500件、救護者通知を呼び出し者へ500件送る前提 |
| 帯域(GB) | 0.1GB程度 | 一覧取得、詳細入力、通知送信、リアルタイム再取得を含む |
| データベース量(GB) | 0.02GB以下 | `item2_calls`、監査ログ、通知関連の保存を含む |
| 同時接続数 | 50接続程度 | 厚生部50名が同時に画面を開く前提 |
