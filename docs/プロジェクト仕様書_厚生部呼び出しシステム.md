# 厚生部呼び出しシステム 仕様書

## 1. 概要

厚生部呼び出しシステムは、利用者が緊急または不急の対応を厚生部へ依頼し、厚生部側が一覧・チャット・現地対応を通じて対応するための機能である。

本機能は `src/features/item2/` に実装する。

### 目的
- 利用者が必要な支援をすぐに厚生部へ依頼できるようにする
- 厚生部が対応状況を可視化し、誰がチャット対応するか、誰が現地へ向かうかを分けて管理できるようにする
- 対応中の会話をリアルタイムで共有しつつ、最終的なログを Supabase に保存できるようにする

### 技術方針
- フロントエンド: React Native (Expo)
- バックエンド: Supabase
- リアルタイム: Supabase Realtime
- ローカル一時保存: SQLite
- 通知配信: 統合システム側で実行
- 実装配置: `src/features/item2/`

## 3. 用語定義

- `calls.assigned_to`
  - 現地に向かう人の配列
  - 緊急対応で「向かう」を押したメンバーを管理する
- `chats.assigned_to`
  - チャット対応者の配列
  - チャット通知の主な宛先になる
- `requester`
  - 呼び出しを行った利用者
- `staff`
  - 厚生部メンバー
- `admin`
  - 管理者
- `system message`
  - システムが自動で送信するチャットメッセージ
- `presence`
  - そのユーザーが当該チャット画面を現在開いているかどうかを示す状態

## 4. 主な機能（利用者）

### 4.1 呼び出し作成
- 緊急または不急を選択できる
- 場所を入力する
- 緊急時は状況を自由入力する
- 不急時は「何をしてほしいか」をプルダウンで選択する
  - 例: 絆創膏が欲しい、熱を測りたい、その他

### 4.2 不急の「その他」選択時
- 呼び出し作成直後に、システムメッセージを自動送信する
- 文言:
  - 「厚生部に何をして欲しいのか教えてください」

### 4.3 利用者チャット
- 呼び出し作成後、自動でチャットが開始される
- チャットは LINE のような一般的なメッセージ UI を目指す
- 現時点では以下は未対応とする
  - 画像送信
  - スタンプ
  - 電話
- メッセージの編集は不可
- メッセージの削除は可能
- 削除後は「削除した」ことが分かる記録を残す

## 5. 主な機能（厚生部）

厚生部の画面では、以下の2種類の見方を提供する。

- 対応一覧画面・緊急対応画面は、厚生部ロールまたは管理者ロールを持つユーザーのみ表示する

### 5.1 対応一覧画面
- すべての呼び出しを一覧表示する
- 各カードには以下を表示する
  - 呼び出し種別（緊急 / 不急）
  - 内容要約
  - 場所
  - 呼び出し者名
  - 呼び出し時刻
  - ステータス
  - チャット対応者
- `chats.assigned_to` が空の場合、チャット対応者欄は「未決定」と表示する
- 呼び出しカードを押すとチャット画面を開く

### 5.2 緊急対応画面
- 緊急呼び出しのみを対象に一覧表示する
- 各カードに「向かう」操作を表示する
- この画面では `calls.assigned_to` を操作する
- `calls.assigned_to` が空の場合は「向かう」ボタンを表示する
- `calls.assigned_to` に担当者がいる場合は、その担当者名を表示する

### 5.3 チャット対応者の管理
- チャットを開いた厚生部メンバーは、必要に応じて `chats.assigned_to` に追加できる
- `chats.assigned_to` は複数人登録可能
- 対応者の追加・削除・再割当は厚生部全員が可能
- 操作はモーダルウィンドウで行う
  - ボタン: 「確定」「戻る」
  - 「戻る」を押した場合は変更しない
  - 理由入力は不要

### 5.4 向かう人の管理
- 緊急呼び出しに対して、現地に向かう人は `calls.assigned_to` で管理する
- `calls.assigned_to` も複数人登録可能
- 追加・削除・再割当は厚生部全員が可能
- 操作はモーダルウィンドウで行う
  - ボタン: 「確定」「戻る」
  - 「戻る」を押した場合は変更しない

### 5.5 向かう人決定時の自動メッセージ
- 緊急呼び出しで `calls.assigned_to` が追加された場合、チャットへ system message を送る
- 文言:
  - 「〇〇部の××さんが向かっています。」
- 役職表記ルール:
  - 対象ユーザーが厚生部ロールを持っている場合は `厚生部` と表示する
  - 厚生部ロールがない場合は、そのユーザーのロール一覧を自由な順で連結して表示する

### 5.6 対応終了
- 厚生部全員が「対応終了」ボタンを押せる
- 押下時は確認ダイアログを表示する
- 確定後、ステータスを `resolved` に更新する
- 対応終了後は再開不可とする

## 6. チャット仕様

### 6.1 基本方針
- チャット体験は LINE に近いものとする
- チャット画面を開いている間に新規メッセージが届いた場合、その場で即時表示する
- メッセージは Supabase Realtime を通してリアルタイム受信する

### 6.2 メッセージ送受信
- 新規メッセージはクライアントで即時表示する
- 同時に SQLite に一時保存する
- 対応終了までは、チャットログの正本はクライアントローカルに保持する
- 対応終了時にまとめて Supabase に保存する

### 6.3 削除
- メッセージの編集は不可
- メッセージの削除は可能
- 削除後は本文の代わりに削除済み表示を行う
- 削除操作は監査ログに残す

### 6.4 途中参加者
- 途中参加者は Supabase に保存済みのメッセージを取得して閲覧できる
- まだ Supabase に保存されていないローカルメッセージについては、Realtime 受信とクライアント間同期で閲覧可能にする
- 途中参加者への補完は以下で行う
  - 第一手段: Supabase Realtime
  - 補助手段: P2P 同期（将来拡張可能な設計）

## 7. リアルタイム設計（Supabase Realtime）

### 7.1 採用方針
- リアルタイム通信は `Supabase Realtime` を使う
- Socket.IO は採用しない
- Supabase Realtime Channel でメッセージ購読・presence・状態同期を行う

### 7.2 チャネル設計
- チャット単位でチャンネルを分ける
- 例:
  - `call:{call_id}`
- 取り扱う主なイベント
  - 新規メッセージ通知
  - 削除通知
  - 対応者更新通知
  - 向かう人更新通知
  - presence 更新通知

### 7.3 presence
- チャットを開いたクライアントは Realtime Channel に参加する
- presence 情報で「現在そのチャットを開いているか」を管理する
- heartbeat により状態を維持する
- TTL は 30 秒とする

### 7.4 チャット表示中の新規メッセージ
- チャット画面を開いている状態で新規メッセージが届いた場合、Realtime で即時表示する
- 開いているユーザーには、そのチャットに関する通知は抑制する
- ただし、そのユーザー以外の対応者には通常どおり通知を送る

---

## 8. ローカル保存と Supabase 同期

### 8.1 ローカル保存
- チャットメッセージは SQLite に保存する
- 保存項目例
  - `temp_id`
  - `call_id`
  - `sender_id`
  - `body`
  - `client_ts`
  - `is_deleted`
  - `system_flag`

### 8.2 バッチ保存
- 対応終了時にローカルメッセージをまとめて Supabase へ送信する
- RPC で一括保存する
- サーバーは `temp_id` を使って重複排除する
- サーバー保存後に `server_id` と `server_ts` を返す
- 表示順は `server_ts` を優先する

### 8.3 バッチ失敗時
- リトライは exponential backoff を用いる
- 最大 5 回まで自動再試行する
- それでも失敗した場合は、手動再送 UI を表示する

### 8.4 正本の扱い
- 対応中はローカル保存を中心とする
- 対応終了後は Supabase 保存データを正本とする

## 9. 通知仕様

### 9.1 通知先
- 新規メッセージの通知対象は以下の和集合とする
  - `chats.assigned_to`
  - `calls.assigned_to`

### 9.2 通知送信ルール
- 対応者が複数いる場合、対応者全員に通知を試行する
- そのうち一人でも通知成功した場合は、それ以上フォールバックしない
- 対応者全員への通知が失敗した場合のみ、厚生部全員へフォールバック通知を送る
- フォールバック通知には以下を明記する
  - 「対応者への通知送信失敗」

### 9.3 チャット画面表示中の通知抑制
- `Supabase Realtime presence` を使って、対象ユーザーが当該チャットを開いているか判定する
- 開いているユーザーにはそのチャットの通知を送らない

---

## 10. 既読・未読仕様

### 10.1 既読になる条件
- チャット対応者がチャットを開いた場合、その対応者は既読とする
- チャット対応者ではないユーザーがチャットを開いても、自動既読にはしない
- ただし非対応者向けに「既読にする」操作を用意する
- 非対応者が返信した場合、その時点で既読扱いとする

### 10.2 未読バッジ
- 未読バッジは厚生部全員に表示する
- 表示イメージは LINE に近いものとする

## 11. ステータス遷移

- `unhandled`
  - 初期状態
- `in_progress`
  - 以下のいずれかが起きた時に移行する
    - 厚生部メンバーが最初のメッセージを送信した
    - `chats.assigned_to` が初回設定された
    - `calls.assigned_to` が初回設定された
- `resolved`
  - 厚生部メンバーが対応終了を実行した
- `resolved` から再開は不可とする

---

## 12. RLS（想定）

### requester
- 自分が作成した `calls` を read できる
- 自分が関係する `chats` を read できる
- 自分が作成した呼び出しに対してメッセージを送信できる

### staff
- 全 `calls` と全 `chats` を read できる
- 全 `calls` と全 `chats` に対して必要な write を行える
- `calls.assigned_to` と `chats.assigned_to` の直接更新は禁止し、RPC 経由のみ許可する
- 対応終了を実行できる

### admin
- 全権限を持つ
- 監査ログの閲覧・エクスポートが可能

---

## 13. RPC（サーバー側関数）案

- `set_chat_assignees(chat_id, user_ids[], actor_id)`
  - チャット対応者を追加・削除・再設定する
- `set_call_assignees(call_id, user_ids[], actor_id)`
  - 現地に向かう人を追加・削除・再設定する
- `batch_upload_messages(call_id, messages[], actor_id)`
  - ローカル保存中のチャットログをまとめて Supabase へ保存する
- `send_notification(target_ids[], payload)`
  - 統合システムへの通知送信を実行する
- `mark_message_deleted(chat_id, message_id, actor_id)`
  - メッセージを削除済みとして記録する
- `resolve_call(call_id, actor_id)`
  - 対応終了を実行する

---

## 14. 監査ログ

- 以下を必須で保存する
  - `event_type`
  - `call_id`
  - `chat_id`
  - `old_value`
  - `new_value`
  - `actor_id`
  - `actor_name`
  - `timestamp`
- 理由入力は不要のため `reason` は任意項目とする
- 以下の操作は必ず監査ログ対象とする
  - チャット対応者の追加・削除・再割当
  - 向かう人の追加・削除・再割当
  - メッセージ削除
  - 対応終了
