# プロジェクト仕様書_アクセス権限制御

最終更新日: 2026-03-30
対象実装: `src/features/item7`

---

## 1. 目的

ロール（部署・役職）ごとの画面アクセス権限を、GUIで確認・編集できる管理画面を提供する。
現在 `roles` テーブルの `permissions.screens` に格納されているアクセス権を、SQLを直接操作せずに管理可能にする。

---

## 3. アクセス権限

### 3.1 本画面へのアクセス条件

以下の**いずれか**のロールを持つユーザーのみアクセス可能:

- **システム部**
- **管理者**（Admin / Administrator を含む）

### 3.2 アクセス制御の実装方針

- `permissionService.js` の既存関数を利用し、`item7` を `permissions.screens` に持つロールのみアクセス可能とする
- Supabase の `roles` テーブルで、システム部と管理者の `permissions.screens` に `"item7"` を追加する
- `CustomDrawerContent.jsx` の `ITEM_LABELS` に `7: 'アクセス権限制御'` を追加する

### 4.2 permissions カラム構造（JSONB）

```json
{
  "screens": ["企画・屋台一覧", "item2", "item3", ...]
}
```

- 全ロール共通で `screens` 配列を持つ
- 例外: 企画管理部のみ `features` キーも存在する（`{"item12": ["read", "accept", ...]}`）が、これは画面内機能レベルの権限であり本機能のスコープ外
- **本機能で編集するのは `screens` 配列のみ**。更新時に `features` 等の既存キーを消失させないよう注意する

## 6. 操作フロー

### 6.1 ロール別: 権限編集フロー

```
1. 画面表示 → 全ロール + 全ロールの permissions を一括取得
2. 左パネルでロールを選択
3. 右パネルにチェックリスト表示（現在の権限状態を反映）
4. チェックを変更（複数変更可）
5. 「保存」ボタン押下
6. 確認ダイアログ表示（「{ロール名} のアクセス権限を更新しますか？」）
7. OK → roles.permissions を更新（screens配列のみ。featuresは維持）
8. 成功メッセージ表示 → 一覧のバッジ数を更新
```

### 6.2 項目別: 権限編集フロー

```
1. 左パネルで項目を選択
2. 右パネルに全ロールのチェックリスト表示
3. チェックを変更（複数ロール分の変更可）
4. 「保存」ボタン押下
5. 確認ダイアログ表示（「{項目名} のアクセス権限を更新しますか？」）
6. OK → 変更のあったロールの permissions.screens をそれぞれ更新
7. 成功メッセージ表示 → 一覧のバッジ数を更新
```

### 6.3 エラーハンドリング

| ケース | 対応 |
|---|---|
| ネットワークエラー | エラーメッセージ表示、変更状態は維持（再試行可能） |
| 保存失敗（一部ロール） | 失敗したロール名を表示、成功分は反映済み |
| データ競合（別ユーザーが同時編集） | 最後の保存が優先（楽観的更新） |

## 7. セーフガード

### 7.1 ロックアウト防止

以下の操作は禁止し、UI上で無効化（disabled + ツールチップで理由表示）する:

| 禁止操作 | 理由 |
|---|---|
| **管理者**ロールから `item7`（アクセス権限制御）を外す | 管理者が本画面にアクセスできなくなる |
| **システム部**ロールから `item7`（アクセス権限制御）を外す | システム部が本画面にアクセスできなくなる |

### 7.2 変更の確認

- 保存前に必ず確認ダイアログを表示する
- 「リセット」ボタンで未保存の変更を破棄できる
- 未保存の変更がある状態でロール/項目を切り替える際、警告を表示する

## 8. サービス設計

### 8.1 permissionManageService.js

```
selectAllRoles()
  → SELECT id, name, display_name, permissions FROM roles ORDER BY name
  → 戻り値: ロール一覧（permissions含む）

updateRoleScreens(roleId, newScreens)
  → 既存のpermissionsを取得し、screensのみ差し替えてUPDATE
  → permissions.features は維持
  → 戻り値: 更新後のロールオブジェクト

updateMultipleRoleScreens(updates)
  → updates: [{ roleId, newScreens }, ...]
  → 項目別タブで複数ロールを一括更新する際に使用
  → 各ロールのpermissions.featuresは維持
  → 戻り値: 更新結果の配列
```

### 8.2 更新時のpermissions保全

`permissions` はJSONBカラムのため、`screens` のみを更新する際に `features` を消失させないよう注意:

```javascript
// 正しい更新方法
const updatedPermissions = {
  ...existingPermissions,     // features等を維持
  screens: newScreens,        // screensのみ差し替え
};
```

## 11. 既知の制約事項

### 11.1 item12〜15 の二重アクセス制御

現在 `permissionService.js` の `canAccessManagementSupportScreen()` は、item12〜15 に対して **ロール名ベース**（`ROLE_NAME_ALIASES` / `MANAGEMENT_SUPPORT_SCREEN_ROLES`）のアクセス判定を行っている。これは `permissions.screens` とは別系統の制御。

```javascript
// 現在のロジック（permissionService.js）
const MANAGEMENT_SUPPORT_SCREEN_ROLES = {
  item12: [...ROLE_NAME_ALIASES.management, ...ROLE_NAME_ALIASES.patrol, ...ROLE_NAME_ALIASES.admin],
  item13: [...ROLE_NAME_ALIASES.admin],
  item14: [...ROLE_NAME_ALIASES.accounting, ...ROLE_NAME_ALIASES.admin],
  item15: [...ROLE_NAME_ALIASES.property, ...ROLE_NAME_ALIASES.admin],
};
```

**影響**: 本画面で `permissions.screens` から `item12` を外しても、ロール名が「企画管理部」であれば `canAccessManagementSupportScreen()` により引き続きアクセスが許可される。

**対応方針**: 本機能の実装時に `canAccessManagementSupportScreen()` を `permissions.screens` ベースに統一する。具体的には、ロール名エイリアスによるハードコード判定を廃止し、`canAccessScreen()` に一本化する。これにより本画面での編集が実際のアクセス制御に正しく反映されるようになる。

### 11.2 permissions.features は対象外

`permissions.features`（画面内機能レベルの権限）は本機能では編集しない。現在 `features` を使用しているのは `企画管理部` の `item12` のみであり、これはコード内でハードコードされている部分が多い。将来的に features の管理UIが必要になった場合は別途対応する。

### 11.3 permission名の混在

`permissions.screens` に格納される名前が日本語（`企画・屋台一覧`、`落とし物検索` など）と英語（`item2`、`item12` など）で混在している。本機能ではこの混在を維持し、既存のアクセス制御ロジックとの互換性を保つ。

## 12. DB変更（マイグレーション）

### 12.1 rolesテーブルの初期権限追加

システム部と管理者に `item7` を付与する。

```sql
-- システム部に item7 を追加
UPDATE roles
SET permissions = jsonb_set(
  permissions,
  '{screens}',
  (permissions->'screens') || '"item7"'::jsonb
)
WHERE name = 'システム部'
  AND NOT (permissions->'screens' @> '"item7"'::jsonb);

-- 管理者は既に item7 を含むが、念のため確認・追加
UPDATE roles
SET permissions = jsonb_set(
  permissions,
  '{screens}',
  (permissions->'screens') || '"item7"'::jsonb
)
WHERE name = '管理者'
  AND NOT (permissions->'screens' @> '"item7"'::jsonb);
```
